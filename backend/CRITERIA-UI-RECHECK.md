# F-02 기준 관리 화면·변경 후 재점검 전달안

2026-11-09 이주환 구현. 기준 API·모의 공통 기준 시드는 #95의 코드를 사용한다. 기존 테스트·요청의 출처 문자열·숫자 ID·응답 필드를 유지하며 화면과 재점검 연결을 추가한다. PM이 API.md에 반영할 구현 전달안이며 팀 합의 기록을 대신하지 않는다.

## 기존 계약에 추가한 항목

- POST /criteria, POST /criteria/{id}: 기존 기준 응답에 recheck_case_ids 배열을 추가한다. 이 배열은 재점검 요청 대상이며 완료 증명이 아니다.
- 수정 요청의 expected_version은 선택 항목이다. 기존 요청과 호환하며, 관리 화면은 읽었던 버전을 보내 다른 담당자의 변경을 덮어쓰지 않는다. 버전 불일치는 409다. 값이 모두 같으면 버전을 올리거나 재점검하지 않는다.
- 목록·등록·변경은 기존 담당자 전용이다. 출처는 URL 또는 모의 출처 문자열이다. 화면에서는 HTTP(S) 주소만 링크로 표시하고 나머지는 텍스트로 표시한다.

## 기준 변경과 재점검

같은 절차의 진행 건을 ID 순서로 잠근 뒤 기준을 잠근다. 등록·변경·활성 변경으로 적용 기준 ID·버전이 달라지는 건만 점검·승인·확인 요청을 무효화하고 점검 작업 연결을 끊는다. 변경 이력에 담당자·이전 상태·이전 기준 버전을 보존한다. 완료·취소 건과 무관한 관서의 건은 바꾸지 않는다.

커밋 뒤 기존 US-02 함수로 재점검한다. 입력·PDF와 확인된 기준이 유효하면 자동 점검중 → 담당자 승인 대기로 진행한다. 자료 오류·미확인 기준이면 준비중을 유지하며 이전 결과로 승인·완료할 수 없다. 이전 작업의 늦은 응답은 기존 상태·작업 ID·버전 검사로 폐기한다. 자동 재점검 이력의 처리자는 system:criteria-recheck다.

재점검은 프로세스 내 BackgroundTasks다. 서버 재시작을 견디는 영속 큐는 아니며 중단된 준비중 건은 기존 점검 API로 다시 시작할 수 있다. 실제 LLM 설정이 없으면 MockTransport를 쓴다.

## 화면·시드

모의 지원 담당자 → 기준 관리에서 목록·등록·수정을 실행한다. 본문·출처·확인일·적용 범위를 바꾸면 확인 체크를 해제해 새 내용을 다시 대조하도록 한다. 버전 충돌이면 입력을 보존하고 최신 목록에서 수정 대상을 다시 선택하도록 안내한다. 이용자에게 기준 관리 메뉴를 표시하지 않는다.

시드는 #95의 기존 `DEMO_MODE=1 DEMO_LANGUAGE=vi python -m app.seed`를 사용한다. 공통 기준이 없을 때만 명시적인 모의 기준 1개를 넣는다. 실제 공식 기준이나 법적 검토로 표시하지 않는다. 기존 공통 기준·담당자 수정값은 덮어쓰지 않는다.

## 검증 범위

전용 MySQL의 기존 기준 API 테스트를 그대로 실행하고, 별도 test_criteria_recheck.py에서 변경 후 무효화·완료/취소 보존·관서 범위·자동 재점검·이전 응답 폐기·버전 충돌·이력 실패 롤백을 검증한다. 실제 Gemini 통신·영속 큐·팀원 5명의 사람 실행은 포함하지 않는다. localhost 브라우저 자동화는 모의 데이터로만 수행한다.

Python 3.11.9·고정 의존성·일회용 MySQL 8.4에서 `python -m pytest tests common_tests -q`: 296개와 하위 점검 11개 통과. 기존 httpx TestClient 폐기 예정 경고 1개다. `pip check`, 프론트엔드 build·lint와 `git diff --check`도 통과했다. localhost 브라우저 자동화로 실제 서버의 시드 목록 조회·모의 기준 등록·수정·버전 증가·새로고침 뒤 저장 유지를 확인했다. #95 응답 형식 연결 후 수정 저장도 확인했다. 공유 MCP 사용 기록에는 localhost 브라우저 자동화 사용 사실을 전달해야 한다.
