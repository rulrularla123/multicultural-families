## 2. 서버·화면 작업 순서

1. 개발자1: DATA-MODEL을 작성하고 개발자2·테크리더와 모순을 대조한다. 현재 DESIGN·CODE-STYLE은 빈 양식이라 팀의 확정 여부는 합류 시 확인한다.
2. PM·테스트 담당: 사용자 선택 US-04를 바탕으로 first-feature의 오늘 범위와 테스트할 내용을 확정한다. 개발자1·2는 반려 입력·응답·실패 처리를 합의하고 PM이 API.md에 기록한다.
3. 개발자1: 승인 대기·담당자·유효한 사유를 검사하고, 준비중 전이·초안 무효화·이력을 한 트랜잭션으로 저장한다. 소유자에게 사유를 보여 줄 최소 상세 조회를 연결한다.
4. 개발자2: 담당자 사유 입력·반려 버튼과 소유자 사유 표시 화면을 만든다. 이 서버 작업에서 화면을 대신 만들지 않는다.
5. 테스트 담당: 확정한 완성 기준을 테스트하고 병합 후 일부러 틀린 구현을 시험한다. 서버 자체 점검 결과는 참고로 전달하며 공식 결과로 대신 쓰지 않는다.
6. 합류: 화면의 임시 응답을 실제 API로 교체하고 5명 모두 각자의 Mac·브라우저에서 실행한다. PM이 first-feature 3절에 각자 결과를 옮긴다.

현재는 서버 코드·로컬 자체 점검까지 진행했다. 2번의 공유 계약 확정·4~6번의 화면 통합과 팀 확인은 아직 수행하지 않았다. 이 순서의 미완료 부분을 건너뛰고 팀 전체 기능 완료로 제출하지 않는다.

## 5. 검토할 서버 완료 기준

- 담당자만 승인 대기 건을 공백 제거 후 1자 이상 사유로 반려하며 결과 상태는 준비중이다.
- 처리자·일시·사유·당시 기준 버전을 이력에 보존하고 기존 분석을 무효화한다.
- 빈 사유·다른 상태·권한 위반은 DB 상태·이력을 바꾸지 않는다.
- 소유자는 반려 사유를 조회하되 승인 전·반려된 분석 본문은 받지 않는다.

위 항목은 기존 백로그에 근거한 서버 점검 범위이며, PM·테스트 담당이 작성할 first-feature의 공식 완성 기준을 대신하지 않는다.

## 최신 원격 작업과의 대조 (2026-11-02)

origin/main은 여전히 공유 양식 상태다. 새로 확인한 PM 작업 브랜치 `docs/first-feature-hyun731`의 first-feature는 US-01을 선택하고 있다. 이번 US-04는 사용자가 별도로 선택한 반려 서버 작업이며 팀의 첫 기능을 US-04로 변경하는 PR이 아니다. US-01 범위와 병합 순서·서버 폴더·API 계약을 PM·테크리더와 맞춘 뒤 통합한다. 해당 PM 브랜치를 이 작업에 병합하거나 공유 문서를 덮어쓰지 않았다.

## US-01 추가 작업 계획·실행 (2026-11-03)

최신 사용자 배분은 US-01 생성·목록·Attachment다. 사용자가 협의 대기를 생략하고 1단계까지 진행하도록 지시해, 기존 민건 담당 case_detail router에 구현했다. 상세 선택·요청·응답은 US01-API-PROPOSAL에 기록한다.

- 파일: models·schemas·database·기존 case_detail router·DATA-MODEL, 서버 자체 점검·전달 문서. multipart 파서 의존성 한 항목 추가.
- 순서: 생성 실패 테스트 확인 → 모델·nullable 언어·비공개 원본 저장 → multipart 검증·단일 트랜잭션 → 본인 목록 → 기존 DB 업데이트·실제 HTTP 확인.
- 반영: 상황 원문 코드 포인트 계산, PDF 확장자·시그니처·10MB·1~5개 검사, 모의 이용자 본인 필터, 거절 시 부분 저장 없음.
- 제외: frontend·공유 API·기존 반려 router·인수 조건·타인 acceptance 파일, PDF 추출·LLM 호출·표시 언어 선택·다음 단계 스토리.
- 기존 DB의 필수 언어·원본 컬럼 차이는 명시적 DB 준비 명령으로 처리했다. 입력 상한은 models.py에 모으며 기존 테이블의 DB 제약 값을 바꾸려면 별도 스키마 검토가 필요하다.
- 5명 실행·화면 연결·팀 합의 완료로 기록하지 않는다.

## 추가 위임: US-01 화면 연결 (2026-11-03)

사용자가 화면 담당자의 위임을 전달해 이 작업에서 US-01 실제 API 연결까지 처리했다. 앞 절의 frontend 제외는 이 추가 범위에 한해 변경한다. 반려·다음 단계 화면은 제외한다.

- 기존 frontend/types·api/cases·MyCasesScreen·CaseForm·관련 CSS만 조정하고 mockCases를 제거했다.
- 흐름: 모의 이용자 선택 → 본인 목록 → FormData 생성 → 입력 오류 또는 성공 → 목록 갱신.
- 새로고침 지속성·계정 분리·서버 오류·재시도를 실제 Chrome·MySQL로 검증했다.
- 기존 디자인을 다시 만들거나 화면 담당자가 별도로 실행·합의했다고 기록하지 않았다.
