# US-06 보완 처리 전달안

2026-11-09 이주환 구현. 기존 PreparationItem·CaseApproval과 US-05·07 API를 사용한다. PM이 API.md에 반영할 구현 계약이며 팀 합의 기록을 대신하지 않는다. 공유 모델·기존 테스트·준비 체크/완료 API 구현은 변경하지 않았다.

## API

기존 X-Demo-Account를 사용한다. 미인증 401, 다른 이용자·역할 위반 403, 없는 건 404, 상태·승인 버전 충돌 409, 잘못된 입력 422다. 오류는 FastAPI detail 형식이다.

| 요청 | 권한·상태 | 입력 |
| --- | --- | --- |
| GET /cases/{id}/supplement | 소유자·담당자. 승인 공개 이후만 | 없음 |
| POST /cases/{id}/supplement | 담당자, 준비 확인 요청 → 보완 요청 | approval_id, items: [{id, reason}] |
| POST /cases/{id}/start-revision | 해당 이용자, 보완 요청 → 서류 준비중 | approval_id |
| POST /cases/{id}/resolve-supplements | 담당자, 준비 확인 요청 유지 | approval_id, item_ids: [id], reason |

응답은 case_id, approval_id, status, can_request, can_restart, can_resolve, items다. 항목에는 승인된 한국어·베트남어, prepared, supplement_reason, supplement_resolved가 있다. 점검 초안·처리자 ID를 내보내지 않는다. 완료된 건은 당시 승인 스냅샷을 읽기 전용으로 조회하며 취소 건은 409다.

모든 변경은 현재 승인 ID·상황/서류/기준 버전을 검사한다. 현재 건·승인에 속한 항목만 선택할 수 있다. 보완 항목 1~100개, 각 사유는 공백 제거 후 1~10,000자이며 ID 중복·빈 사유·다른 항목·추가 필드는 거절한다. 거절 시 상태·항목·이력이 바뀌지 않는다. 상태·항목·이력을 한 트랜잭션으로 처리한다.

## 보완 흐름과 완료 연결

1. 담당자가 승인 항목과 사유를 지정한다. 대상 항목은 supplement_resolved=false다.
2. 이용자가 수정 시작을 누르면 미해결 보완 항목만 prepared=false(아직)로 바뀐다. 사유·미해결 상태는 보존한다.
3. 이용자는 기존 POST /cases/{id}/preparation-items로 준비 상태를 저장하고 POST /cases/{id}/request-confirmation으로 다시 요청한다. 준비함으로 체크해도 보완 해소 상태는 바뀌지 않는다.
4. 담당자는 준비함·확인 필요 없음인 미해결 항목을 선택하고 처리 사유를 남겨 해소한다. 해소 확인은 user-flows.md의 "US-05 재요청 후 담당자가 보완 처리를 확인"에 해당한다. 보완 사유는 보존하고 supplement_resolved만 true로 바꾼다.
5. 기존 US-07 완료 조건을 충족해야 완료할 수 있다. 미해결 항목이 남으면 완료가 거절된다. 완료·취소 이후 보완 요청·수정 시작·해소 변경은 거절한다.

## 화면

담당자 검토 상세와 이용자 준비 건 상세에 보완 영역을 연결했다. 서버가 응답한 역할별 실행 가능 여부로 버튼을 표시한다. 이용자는 보완 대상의 준비 상태를 저장한 뒤 확인을 다시 요청한다. 저장하지 않은 선택 변경이 있으면 재요청 버튼을 비활성화한다. 화면은 임시 응답이 아닌 실제 API를 사용하며 한국어·베트남어 항목과 허가가 아니라는 두 언어 문구를 표시한다. 고정 문구·모의 시드의 베트남어에 대한 사람 검토 완료를 주장하지 않는다.

## 모의 시드

빈 모의 DB에서 backend의 `DEMO_MODE=1 python -m app.supplement_seed`를 실행한다. DATABASE_URL은 기존 모의 DB 설정을 사용한다. 준비 건 1106과 모의 승인·준비 항목 2개가 생성된다. 소유자는 demo-user-1, 상태는 준비 확인 요청이다. 승인 이력을 실제 검토 이력으로 표시하지 않으며 모의 자료임을 본문에 명시한다. 기존 1106번 건은 덮어쓰지 않는다. 공통 기준이 있으면 현재 확인된 공통 기준을 재사용하고 버전을 모두 연결한다. 미확인 공통 기준이 있으면 이를 바꾸지 않고 별도의 빈 모의 DB 사용을 안내한다.

## 검증

Python 3.11.9·고정 의존성·일회용 MySQL 8.4에서 `python -m pytest tests common_tests -q`: 312개와 하위 점검 11개 통과. US-06 테스트 38개는 역할·입력·상태·버전·끝 상태·롤백·보완 미해결 완료 거절·해소 후 완료·시드 재실행을 검사한다. 기존 TestClient의 httpx 폐기 예정 경고 1개다. 프론트엔드 build·lint와 git diff --check도 통과했다.

별도 모의 DB와 localhost 브라우저 자동화로 담당자 보완 요청 → 이용자 사유 조회·수정 시작 → 대상 항목 아직 초기화 → 준비함 저장 → 확인 재요청 → 담당자 해소 확인까지 실행했다. 완료 API 연결은 테스트로 확인했다. 공유 MCP 사용 기록에는 localhost 브라우저 자동화 사용 사실을 전달해야 한다. 실제 서류·실제 Gemini·팀원 5명 사람 실행·베트남어 검토자 확인은 이 검증에 포함하지 않는다.
