## 1. 개요

- 프로젝트명: 다문화가족 체류 행정 준비 도우미 (가칭)
- 목적: 이용자가 설명한 상황과 보유 서류를 공식 기준에 대조해 주의점과 추가 준비물을 안내하고, 담당자의 검토를 거쳐 체류기간 연장을 준비하도록 돕는다.
- 사용자: F-6-1 체류기간 연장을 준비하는 결혼이민자와 한국인 배우자, 준비 내용을 검토하는 지원 담당자.
- 개발 기간: 수업 프로젝트 8주 안에 최종 데모를 마친다. 첫 데모는 3주차에 진행하며, 남은 개발일과 실제 작업 가능 시간은 미정이다.

클라이언트는 알맞은 서류를 고르는 데 시간이 가장 많이 들었다고 설명했고, 상황에 맞는 서류 안내와 자동 점검을 요청했다. 한국어와 배우자 모국어를 함께 보여 주는 것, 모든 준비 건에 담당자 승인이 필요하다는 것도 미팅에서 확인했다.

이번 MVP는 F-6-1 한 유형에 대해 모의 상황과 모의 PDF로 준비 건 생성부터 준비 확인 완료까지 연결한다. 자동 점검은 담당자의 대조 작업을 돕고, 이용자에게는 담당자가 승인한 결과를 공개한다. 여기서 담당자는 서비스의 지원 담당자이며 출입국기관의 허가 담당자가 아니다.

서류 선택 시간과 담당자의 검토·반복 안내 시간을 줄이는 것이 목표다. 현재 소요 시간과 개선 효과는 아직 측정하지 않았고, 목표 수치도 정하지 않았다. 준비 확인 완료는 실제 민원 접수나 체류기간 연장 허가를 뜻하지 않는다.

## 2. 사용자 여정

상태 이름과 흐름은 `user-flows.md`가 기준으로 삼은 제안서 v2 Ⅳ-12를 따른다. 초기 도메인 문서의 `안내 검토 대기`와 다른 점은 마지막 문서 대조 기록에 남겼다.

핵심 대상: **절차 준비 건** (선정 주제 B, 제안서 v2 Ⅳ-12)
지나가는 상태: 준비중 → 자동 점검중 → 담당자 승인 대기 → 서류 준비중 → 준비 확인 요청 → 준비 확인 완료 (6개)

### 첫 데모 흐름

데모 조건: 모의 계정 2개(이용자 1, 지원 담당자 1), F-6-1 체류기간 연장 1유형, 가상 상황 설명과 식별정보가 없는 모의 PDF 서류, 담당자가 미리 등록한 공통 기준 1개 버전.

| 순서 | 누가 | 무엇을 하는가 | 이때 상태 | LLM 관여 |
| --- | --- | --- | --- | --- |
| 1 | 이용자 | 지원 유형 F-6-1을 고르고 상황을 설명한 뒤 모의 PDF 서류를 올려 준비 건을 만든다 | (시작) → 준비중 | 아니오 |
| 2 | 시스템 | 입력 형식과 식별정보 포함 여부를 검사하고 통과하면 자동 점검을 시작한다 | 준비중 → 자동 점검중 | 아니오 (규칙 검사) |
| 3 | 시스템 | 등록된 기준과 서류를 대조해 주의점·누락 가능성·추가 준비 서류 후보·근거 출처를 담당자용 결과로 저장한다 | 자동 점검중 → 담당자 승인 대기 | 예 (분석 초안 생성) |
| 4 | 지원 담당자 | 서류, 기준 출처·기준일, 분석 결과를 확인하고 승인한다. 승인된 결과가 한국어와 배우자 모국어로 이용자에게 공개된다 | 담당자 승인 대기 → 서류 준비중 | 예 (승인 대상인 초안. 상태는 담당자가 바꿈) |
| 5 | 이용자 | 공개된 주의점과 추가 서류를 보고 준비 항목을 체크한 뒤 확인을 요청한다 | 서류 준비중 → 준비 확인 요청 | 아니오 |
| 6 | 지원 담당자 | 승인 결과가 현재 기준 버전과 같고, 미해결 보완·확인 필요 항목이 없고, 모든 항목이 "준비함"인지 확인해 완료 처리한다. 화면에 "민원 접수·허가 완료가 아님"을 표시한다 | 준비 확인 요청 → 준비 확인 완료 | 아니오 |

### 반려·보완·취소 경로

첫 데모는 위 정상 경로를 보여 준다. 반려·보완·취소도 필수 기능이며, 아래 경로와 8절의 인수 조건에서 다룬다.

| 경로 | 필수 스토리 | 누가·조건 | 상태 전이 / 정상 흐름 복귀 |
| --- | --- | --- | --- |
| 담당자 반려 | [US-04](requirements/backlog.md#us-04-담당자가-분석-결과를-반려하기) | 담당자가 승인 대기 건에 사유를 기록 | 담당자 승인 대기 → 준비중. 이용자가 자료를 고쳐 US-02로 재점검 |
| 보완·되돌림 | [US-06](requirements/backlog.md#us-06-담당자가-보완-요청하고-이용자가-다시-준비하기) | 담당자가 항목·사유를 지정하고 본인 이용자가 수정 시작 | 준비 확인 요청 → 보완 요청 → 서류 준비중. US-05 재요청 후 담당자가 보완 처리를 확인 |
| 이용자 취소 | [US-08](requirements/backlog.md#us-08-이용자가-진행-중인-준비-건-취소하기) | 본인 이용자가 진행 중 6개 상태에서 취소 확인 | 진행 중 상태 → 취소 완료. 끝 상태이며 재진행은 새 건으로 시작 |

- 기준·상황·서류 변경에 따른 재점검(각 진행 상태 → 자동 점검중)은 첫 데모 흐름에 넣지 않고, backlog.md 공통 조건과 US-02 인수 조건에서 다룬다
- 자동 점검 실패·근거 부족 경로는 US-02의 실패 인수 조건에서 다룬다

## 3. 기능 명세

기능 번호는 제안서 v2 Ⅳ-11, 스토리 번호와 우선순위는 백로그를 따른다. 같은 기능을 여러 스토리로 나눈 경우에도 기능 번호를 새로 만들지 않는다.

| 기능 ID | 스토리 (US) | 기능 | 우선순위 | 경로 (정상 / 취소·반려) | LLM 관여 |
| --- | --- | --- | --- | --- | --- |
| F-01 | US-01 | 상황 설명·모의 PDF·표시 언어로 준비 건 생성 | 필수 | 정상 | 아니오 |
| F-02, F-03, F-09 | US-02 | 등록 기준에 따른 서류 자동 점검과 담당자 부재 중 점검 | 필수 | 정상, 점검 실패 처리 | 예 (담당자용 분석 초안) |
| F-04, F-05 | US-03 | 담당자 승인 후 한국어·모국어로 결과 공개 | 필수 | 정상 | 예 (승인 대상이 LLM 결과, 번역 방식은 미정) |
| F-04 | US-04 | 사유를 남기고 분석 결과 반려 | 필수 | 취소·반려 | 예 (반려 대상이 LLM 결과) |
| F-06 | US-05 | 준비 여부 체크와 확인 요청 | 필수 | 정상 | 아니오 |
| F-07 | US-06 | 담당자 보완 요청과 이용자 수정 시작 | 필수 | 취소·반려 (보완·되돌림) | 아니오 |
| F-07 | US-07 | 최신 기준과 준비 상태 확인 후 완료 | 필수 | 정상 | 아니오 |
| F-08 | US-08 | 진행 중인 본인 건 취소와 이력 기록 | 필수 | 취소·반려 | 아니오 |

F-02는 문서 간 범위가 맞지 않는다. 백로그 US-02와 MVP 포함 표에는 기준 등록·변경이 들어 있지만, 백로그의 별도 제외 설명에는 시드 데이터만 사용한다고 적혀 있다. US-02의 기능 대응과 인수 조건은 유지하되, 등록·변경 기능의 최종 범위는 팀 검토가 필요하다.

US-09 이력 조회 화면은 선택 스토리다. 필수 스토리에서 요구하는 승인·반려·보완·취소 이력의 기록과 구분한다. F-10 알림 기능도 이번 필수 기능에 넣지 않으며, 화면 안의 대기·보완 상태 표시는 유지한다.

## 5. 메뉴·화면 구조

백로그에 등장하는 화면과 필요한 내용을 정리했다. 메뉴 이름, 화면을 나누는 방식과 배치는 미정이다.

| 화면 | 보여 줄 정보 | 입력·버튼 | 연결된 기능 ID |
| --- | --- | --- | --- |
| 이용자 준비 건 목록 | 본인 준비 건, 생성 일시, 현재 상태 | 새 준비 건 만들기, 상세 열기 | F-01, F-08 |
| 준비 건 생성 | 지원 유형, 입력·파일 거절 사유 | 상황 설명, 모의 PDF, 표시 언어 선택, 제출 | F-01 |
| 이용자 준비 건 상세 | 검토 중 상태, 승인된 두 언어 결과·근거 출처·기준일, 반려·보완 사유, 준비 항목 | 준비함/아직 선택, 확인 요청, 수정 시작, 진행 중 건 취소 | F-04, F-05, F-06, F-07, F-08 |
| 담당자 검토 | 상황·서류, 분석 결과, 기준 출처·기준일·버전, 실패·확인 필요 항목 | 분석 항목 수정·삭제, 승인, 사유 입력 후 반려 | F-03, F-04, F-09 |
| 담당자 준비 확인 | 준비 여부, 아직인 항목 수, 보완 항목, 승인 결과와 현재 버전의 일치 여부 | 보완 항목·이유 입력, 보완 요청, 완료 | F-06, F-07 |

담당자용 분석 본문은 승인 전 이용자 화면에 표시하지 않는다. 기준 등록 화면은 F-02의 포함 여부를 정한 뒤 구체화한다. 별도 이력 조회 화면은 선택 범위로 남긴다.

## 6. 데이터 구조

백로그에서 필요한 데이터의 이름과 핵심 항목을 모았다. 테이블 분리, 필드 타입과 상세 관계는 미정이다.

| 모델 | 필드 | 설명 |
| --- | --- | --- |
| 절차 준비 건 | 준비 건 ID, 소유자, 상황 설명, 표시 언어, 상태(status) | 이용자 본인의 준비 단위. 지원 유형은 MVP에서 F-6-1로 제한한다 |
| 첨부 서류 | 준비 건 ID, 파일명, 파일 크기, 추출 텍스트, 서류 버전 | 모의 텍스트 PDF만 사용한다. 원본 파일을 LLM에 보내지 않는다 |
| 적용 기준 | 기준 ID, 기준 본문, 출처, 기준일·확인일, 버전 | 분석과 승인에 사용한 기준을 추적한다. 등록·변경 범위는 문서 대조 후 확정한다 |
| 점검 결과 | 준비 건 ID, 상황·서류·기준 버전, 분석 항목, 근거 기준 ID, 실패·확인 필요 사유 | 이전 입력에 대한 결과가 현재 건에 반영되지 않도록 버전을 연결한다 |
| 준비 항목 | 준비 건 ID, 승인된 항목 내용, 준비 여부, 보완 사유, 보완 처리 여부 | 준비 여부는 준비함/아직으로 표시한다. 미해결 보완은 완료를 막는다 |
| 처리 이력 | 준비 건 ID, 변경 전·후 상태, 처리자, 처리 일시, 처리 사유·적용 기준 버전 | 승인·반려·보완·취소의 근거를 남긴다. 조회 화면은 선택 기능이다 |

`status`는 `준비중`, `자동 점검중`, `담당자 승인 대기`, `서류 준비중`, `준비 확인 요청`, `보완 요청`, `준비 확인 완료`, `취소 완료`를 사용한다. 이 목록은 사용자 흐름과 백로그 기준이며, 초기 도메인 문서와의 차이는 문서 대조 기록에서 다룬다.

## 7. 상태와 LLM의 역할

### 상태 전이

핵심 대상은 절차 준비 건이다. 상태를 바꾸는 주체와 조건은 다음과 같다.

| 지금 상태 | 다음 상태 | 주체·조건 |
| --- | --- | --- |
| 시작 | 준비중 | 이용자가 유효한 상황 설명·모의 PDF·표시 언어를 제출 |
| 준비중 | 자동 점검중 | 시스템이 입력·식별정보 검사를 통과시키고 적용할 등록 기준을 확인 |
| 자동 점검중 | 담당자 승인 대기 | 시스템이 분석 결과·근거를 저장하거나 점검 오류·시간 초과 사유를 기록. 자동 승인으로 처리하지 않음 |
| 담당자 승인 대기 | 서류 준비중 | 담당자가 현재 상황·서류·기준 버전과 결과를 확인하고 미해결 실패·확인 필요 사유를 해소한 뒤 승인 |
| 담당자 승인 대기 | 준비중 | 담당자가 사유를 입력해 반려 |
| 서류 준비중 | 준비 확인 요청 | 본인 이용자가 모든 준비 항목에 준비함/아직을 선택하고 요청. 아직인 항목이 있어도 접수 |
| 준비 확인 요청 | 보완 요청 | 담당자가 보완 항목 1개 이상과 항목별 이유를 지정 |
| 보완 요청 | 서류 준비중 | 본인 이용자가 수정 시작. 보완 항목은 아직으로 초기화 |
| 준비 확인 요청 | 준비 확인 완료 | 담당자가 현재 버전 일치, 미해결 보완·확인 필요 0개, 모든 항목 준비함을 확인 |
| 진행 중 상태 | 자동 점검중 | 상황·PDF·적용 기준이 변경되면 이전 분석·승인·확인 요청을 무효화하고 재점검. 유효하지 않은 자료는 수정 후 재점검 |
| 진행 중 6개 상태 | 취소 완료 | 본인 이용자가 취소 확인 후 취소 |

입력 검사에서 식별정보가 발견되거나 PDF 텍스트를 추출하지 못하거나 적용할 기준이 없으면 LLM을 호출하지 않고 `준비중`을 유지한다. 점검 시작 뒤 LLM 호출이 실패한 경우는 실패 사유를 남겨 `담당자 승인 대기`로 보낸다.

상황·서류·기준 변경 전의 결과나 취소 후 도착한 결과는 현재 분석·승인·상태에 반영하지 않는다. 준비 여부 체크 변경과 상황·PDF 자체의 변경은 구분한다. `준비 확인 완료`와 `취소 완료`는 끝 상태이며, 다시 진행하려면 새 준비 건을 만든다.

### LLM이 맡는 일과 사람이 확인하는 일

LLM은 허용된 상황 설명·PDF 추출 텍스트와 등록 기준을 대조해 주의점, 누락 가능성, 추가 준비 서류 후보와 근거를 정리한다. 근거가 없는 항목은 확인 필요로 남긴다. 모국어 번역에 LLM을 사용할지는 아직 정하지 않았다.

도메인 문서의 원칙인 “담당자가 모든 초안을 원문과 대조해 수정·승인. 필수 목록·완료 판단은 규칙·사람이 담당”을 유지한다. 자동 점검 시작과 종료는 시스템이 상태에 기록할 수 있지만, 담당자가 확인·승인하기 전에는 승인 여부와 준비 완료 상태가 바뀌지 않는다. 담당자 부재 중에도 점검은 수행하되 결과는 담당자용으로 저장하고 승인 대기를 유지한다.

LLM은 서류 진위, 개별 사건의 법적 결론이나 허가 가능성을 판정하지 않는다. 승인·반려·보완 판정·최종 완료도 LLM 응답만으로 실행하지 않는다.

### LLM에 보내지 않을 정보

초기 도메인 문서의 전송 금지 항목은 “실명·연락처·등록번호·여권번호·주소·실제 서류 이미지. 가상 사례와 허용된 비식별 입력만 사용”이다. 백로그에 따라 이용자 계정 ID·이메일과 PDF 원본 파일도 요청 본문에 넣지 않는다.

MVP의 자동 검사는 외국인등록번호, 여권번호, 휴대전화번호 패턴을 대상으로 한다. 이것으로 모든 식별정보를 검출할 수 있다고 보지 않는다. 실명·주소 자동 검출은 범위에서 제외하며, 식별정보가 없는 가상 상황과 모의 PDF만 사용한다. 입력 검사를 통과한 상황 설명, PDF 추출 텍스트, 지원 유형, 등록 기준 본문·출처·기준일만 LLM 요청에 사용한다.

## 8. 완료 기준

백로그의 필수 스토리 US-01~US-08 인수 조건을 그대로 옮겼다. 체크박스는 앞으로 확인할 조건이며, 구현이나 테스트가 끝났다는 뜻이 아니다. 상황 설명 1,000자, PDF 5개·각 10MB, LLM 60초는 백로그에 적힌 설계 검토값으로 고객 확정값은 아니다.

### US-01 상황 설명과 서류로 준비 건 만들기

기능 ID: F-01

- [ ] (정상) 이용자가 지원 유형 F-6-1, 상황 설명 1자 이상 1,000자 이하, PDF 파일 1~5개(각 10MB 이하), 표시 언어(모국어) 1개를 제출하면 준비 건이 1개 생성되고 상태는 `준비중`, 소유자는 제출한 이용자다. 표시 언어는 US-03·07의 두 언어 표시에 쓰인다.
- [ ] (정상) 생성 직후 이용자의 준비 건 목록에 새 건이 생성 일시와 함께 1줄 추가된다.
- [ ] (경계) 상황 설명 1자·1,000자, 파일 정확히 10MB(10,485,760바이트), 파일 1개·5개는 받는다. 상황 설명 1,001자, 10,485,761바이트 파일, 파일 0개·6개는 거절한다.
- [ ] (실패·거절) PDF가 아닌 파일(확장자 또는 파일 시그니처가 PDF가 아님), 10MB 초과 파일, 파일 0개 또는 6개 이상, 빈 상황 설명(공백·줄바꿈만 있는 경우 포함), 1,000자 초과 상황 설명, F-6-1 외 유형, 표시 언어 미선택 중 하나라도 있으면 준비 건을 만들지 않고 해당 항목과 거절 사유를 표시한다.
- [ ] (권한) 다른 이용자와 로그인하지 않은 사용자는 이 준비 건을 목록·상세에서 볼 수 없고, 상세 주소로 직접 요청하면 403(로그인 안 함은 401)을 받는다.

### US-02 등록된 기준으로 서류 자동 점검하기

기능 ID: F-02, F-03, F-09

- [ ] (정상) `준비중`인 건의 상황 설명·PDF 추출 텍스트가 입력 검사를 통과하고 적용할 등록 기준이 있으면 시스템이 상태를 `자동 점검중`으로 바꾸고 LLM 분석을 요청한다. 상황·서류·적용 기준 버전을 점검 결과에 연결한다.
- [ ] (정상) LLM 분석이 끝나면 결과(주의점, 누락 가능성, 추가 준비 서류 후보, 각 항목의 근거 기준 ID·출처·기준일)를 저장하고 상태를 `담당자 승인 대기`로 바꾼다. 근거 기준 ID가 없는 항목은 "확인 필요"로 표시된다.
- [ ] (정상) 담당자는 공통 기준과 관서별 기준을 구분해 적용 절차·관서·공식 원문·출처·확인일·버전과 함께 등록할 수 있다. 관서별 출처·최신 여부가 확인되지 않았으면 추가 요구를 생성하지 않고 "관서 확인 필요"로 표시한다.
- [ ] (정상) 담당자가 부재하거나 로그인하지 않아도 점검은 수행되고, 종료 후 결과는 담당자용으로 저장되며 `담당자 승인 대기`를 유지한다.
- [ ] (실패·거절) 상황 설명이나 PDF 텍스트에서 식별정보 패턴이 1개 이상 발견되면 LLM을 호출하지 않고 상태를 `준비중`으로 유지하며, 발견된 위치(파일명·페이지 또는 상황 설명)와 수정 안내를 이용자에게 표시한다.
- [ ] (실패·거절) PDF에서 텍스트를 추출하지 못하거나(스캔 PDF 포함) 적용할 기준이 없으면 LLM을 호출하지 않고 `준비중`을 유지하며 자료 수정·담당자 문의를 안내한다. 점검 시작 뒤 LLM 호출이 오류·60초 초과로 끝나면 실패 사유와 "자동 점검 실패"를 기록하고 `담당자 승인 대기`로 보내며 승인으로 처리하지 않는다.
- [ ] (실패·거절) 기준 등록 필수 정보가 빠지면 등록을 거절하고 기존 기준을 유지한다. 기준 등록·변경은 담당자만 실행할 수 있으며 이용자 계정의 요청은 거절한다.
- [ ] (실패·거절) 입력·기준이 변경됐거나 취소된 건의 이전 점검 결과가 늦게 도착하면 현재 분석·승인 여부·상태에 반영하지 않는다.
- [ ] (권한) 자동 점검 결과는 담당자만 조회할 수 있다. 이용자와 다른 이용자가 결과를 요청하면 403을 받고, 이용자 화면에는 "담당자 검토 중"만 표시된다.
- [ ] (LLM) 자동 점검이 끝나도 상태는 `담당자 승인 대기`까지만 바뀐다. LLM 응답의 내용과 관계없이 시스템이 `서류 준비중`·`준비 확인 완료`로 바꾸는 경로가 없다.
- [ ] (LLM) LLM 요청 본문에 식별정보 패턴, 이용자 계정 ID·이메일, PDF 원본 파일(바이너리)이 들어가지 않는다. 보내는 것은 마스킹 검사를 통과한 상황 설명, PDF 추출 텍스트, 지원 유형, 등록된 기준 본문·출처·기준일뿐이다(제안서 Ⅳ-13).

### US-03 담당자가 분석 결과를 승인해 두 언어로 공개하기

기능 ID: F-04, F-05

- [ ] (정상) 담당자가 `담당자 승인 대기` 건을 승인하면 상태가 `서류 준비중`이 되고, 승인자 ID·승인 일시·적용 기준 버전이 이력에 기록된다.
- [ ] (정상) 승인 후 이용자 화면에 승인된 항목이 한국어와 이용자가 고른 모국어로 한 화면에 나란히 표시되고, 항목마다 근거 출처와 기준일이 보인다.
- [ ] (정상) 담당자가 승인 전에 항목을 수정·삭제하면 이용자에게는 수정된 내용만 공개되고, 수정 전 LLM 원문은 이용자 화면에 나오지 않는다.
- [ ] (실패·거절) 결과에 "자동 점검 실패" 또는 "확인 필요" 항목이 남아 있으면 승인 버튼이 비활성화되고 승인 요청을 보내도 상태가 바뀌지 않는다. 담당자가 문서·공식 기준을 확인해 오류 항목을 수정·삭제하거나 확인 필요 사유를 해소하고, 근거와 처리 사유를 이력에 남긴 뒤에만 승인할 수 있다. 미해결 사유를 숨기기 위한 항목 삭제만으로 승인하지 않는다.
- [ ] (실패·거절) 승인 대상의 상황·서류·기준 버전이 현재 버전과 다르면 승인을 거절하고 이전 결과를 공개하지 않는다.
- [ ] (실패·거절) `담당자 승인 대기`가 아닌 상태의 건에 승인을 요청하면 거절되고 상태가 바뀌지 않는다.
- [ ] (권한) 이용자와 다른 이용자는 승인 기능을 실행할 수 없다(요청 시 403, 상태 불변).
- [ ] (LLM) 승인 전에는 이용자가 상세 화면·API 어디에서도 분석 결과를 받을 수 없다. LLM의 승인·완료 제안과 관계없이 담당자가 확인·승인하기 전에는 승인 여부와 준비 완료 상태가 바뀌지 않는다.
- [ ] (LLM) 모국어 번역에 LLM을 쓰는 경우에도 번역 요청에 식별정보 패턴과 계정 정보가 들어가지 않는다(제안서 Ⅳ-13).

### US-04 담당자가 분석 결과를 반려하기

기능 ID: F-04

- [ ] (정상) 담당자가 반려 사유(1자 이상)를 입력해 반려하면 상태가 `준비중`이 되고, 반려자 ID·일시·사유가 이력에 기록된다.
- [ ] (정상) 반려 후 이용자 화면에 반려 사유가 표시되고, 이용자가 상황 설명·PDF를 수정해 다시 제출하면 US-02의 자동 점검이 새로 시작된다.
- [ ] (실패·거절) 반려 사유가 비어 있으면 반려되지 않고 상태가 `담당자 승인 대기`로 유지된다.
- [ ] (권한) 이용자와 다른 이용자는 반려 기능을 실행할 수 없다(요청 시 403, 상태 불변). 반려 사유는 해당 건의 이용자와 담당자만 볼 수 있다.
- [ ] (취소·반려) 상태를 바꾸는 사람은 담당자뿐이며, 조건은 `담당자 승인 대기` 상태와 사유 입력이다. 결과 상태는 항상 `준비중`이다.
- [ ] (LLM) 반려된 분석 결과는 이용자에게 공개되지 않는다. LLM이 반려를 제안하더라도 담당자가 사유를 입력해 반려하기 전에는 `담당자 승인 대기`를 유지한다.
- [ ] (LLM) 반려 사유는 LLM에 보내지 않는다. 담당자가 사유에 식별정보를 적을 수 있기 때문이다(제안서 Ⅳ-13).

### US-05 준비 상태를 체크하고 확인 요청하기

기능 ID: F-06

- [ ] (정상) `서류 준비중` 건에서 이용자가 승인된 항목마다 "준비함/아직" 중 하나를 고르고 확인 요청하면 상태가 `준비 확인 요청`이 되고 요청 일시가 기록된다.
- [ ] (정상) "아직"인 항목이 있어도 확인 요청은 접수되고, 담당자 화면에 "아직" 항목 수가 표시된다.
- [ ] (실패·거절) 하나라도 선택하지 않은 항목이 있으면 요청이 거절되고 미선택 항목이 표시된다. 상태는 `서류 준비중`으로 유지된다.
- [ ] (실패·거절) `서류 준비중`이 아닌 건에서 확인 요청하면 거절되고 상태가 바뀌지 않는다.
- [ ] (실패·거절) 확인 요청의 승인 결과가 현재 상황·서류·기준 버전과 일치하지 않으면 요청을 거절한다. 상황·PDF를 변경하면 이전 결과를 무효화하고 US-02 점검·US-03 재승인 뒤에만 확인 요청할 수 있다.
- [ ] (권한) 다른 이용자와 담당자는 이 건의 준비 체크를 바꾸거나 확인 요청을 할 수 없다(요청 시 403).

### US-06 담당자가 보완 요청하고 이용자가 다시 준비하기

기능 ID: F-07

- [ ] (정상) 담당자가 승인된 항목 중 1개 이상을 고르고 항목마다 이유(1자 이상)를 적어 보완 요청하면 상태가 `보완 요청`이 되고, 이용자 화면에 해당 항목과 이유가 표시된다.
- [ ] (정상) 이용자가 "수정 시작"을 누르면 상태가 `서류 준비중`이 되고, 보완 항목은 "아직"으로 초기화된다. 이후 US-05로 다시 확인 요청할 수 있다.
- [ ] (실패·거절) 항목을 하나도 고르지 않았거나 이유가 빈 항목이 있으면 보완 요청이 거절되고 상태는 `준비 확인 요청`으로 유지된다.
- [ ] (권한) 이용자는 보완 요청을 만들 수 없고, 담당자는 "수정 시작"을 대신 누를 수 없다(각각 403).
- [ ] (취소·반려) `준비 확인 요청` → `보완 요청`은 담당자만, `보완 요청` → `서류 준비중`은 해당 건의 이용자만 바꾼다. 미해결 보완 항목이 1개라도 있으면 US-07의 완료가 거절된다.

### US-07 담당자가 준비 확인 완료하기

기능 ID: F-07

- [ ] (정상) `준비 확인 요청` 건의 승인 결과가 현재 상황·서류·기준 버전과 일치하고, 미해결 보완·확인 필요 항목이 0개이고, 모든 항목이 "준비함"이면 담당자가 완료할 수 있고 상태가 `준비 확인 완료`가 된다.
- [ ] (정상) 완료 화면에 "민원 접수나 체류기간 연장 허가가 아닙니다" 문구가 한국어와 이용자 모국어로 표시된다.
- [ ] (실패·거절) 승인 결과와 현재 상황·서류·기준 버전이 다르거나, 미해결 보완·확인 필요 항목 또는 "아직" 항목이 있으면 완료를 거절하고 사유를 표시한다. 요청 자체로 상태를 변경하지 않으며, 입력·기준 변경에 따른 재점검이 시작된 건을 `준비 확인 요청`으로 되돌리지 않는다.
- [ ] (실패·거절) `준비 확인 완료` 건은 체크·첨부·상태를 바꿀 수 없다. 수정 요청은 모두 거절된다.
- [ ] (권한) 이용자와 다른 이용자는 완료 기능을 실행할 수 없다(요청 시 403, 상태 불변).

### US-08 이용자가 진행 중인 준비 건 취소하기

기능 ID: F-08

- [ ] (정상) 진행 중 6개 상태 중 하나인 본인 건을 이용자가 취소 확인 후 취소하면 상태가 `취소 완료`가 되고, 취소 일시와 취소 전 상태가 이력에 기록된다.
- [ ] (정상) `자동 점검중`에 취소하면 이후 도착한 LLM 결과는 저장되지 않고 상태는 `취소 완료`로 유지된다.
- [ ] (실패·거절) `준비 확인 완료`나 `취소 완료` 건은 취소할 수 없고 요청이 거절된다.
- [ ] (실패·거절) `취소 완료` 건은 수정·확인 요청·승인·완료가 모두 거절된다. 이용자는 새 준비 건을 만들어야 한다.
- [ ] (권한) 다른 이용자와 담당자는 이 건을 취소할 수 없다(요청 시 403, 상태 불변).
- [ ] (취소·반려) 상태를 바꾸는 사람은 해당 건의 이용자뿐이며, 조건은 진행 중 상태다. 결과 상태는 항상 `취소 완료`(끝 상태)다.

## 9. 디자인 방향

- 분위기: 미정.
- 주 색상: 미정.
- 참고 서비스: 미정.
- 반응형 여부: 미정.

한국어와 모국어로 승인 결과를 한 화면에 나란히 보여 주고, 항목별 근거 출처와 기준일을 표시하는 요구는 유지한다. 완료 화면에는 민원 접수나 허가 완료가 아니라는 문구를 두 언어로 표시한다. 색상과 배치는 별도 디자인 검토에서 정한다.

## 10. MVP 범위와 제외

### MVP 포함

MVP 범위 문서의 포함 항목과 이유를 옮겼다. F-02 관련 문서 충돌은 아래 대조 기록에 남겼으며, 이 표만으로 포함 여부가 최종 확정된 것으로 보지 않는다.

| 스토리 | 기능 (F-__) | 왜 필수인가 |
| --- | --- | --- |
| US-01 상황 설명과 서류로 준비 건 만들기 | F-01 | 첫 데모 흐름 1단계. 클라이언트가 체크박스보다 상황 설명 기반 안내를 요청함(피드백 11) |
| US-02 등록된 기준으로 서류 자동 점검하기 | F-02, F-03, F-09 | 첫 데모 흐름 2~3단계. 필수 조건 2(LLM)가 들어가는 자리이며 담당자 부재 중 검증 요구(피드백 4·9). 기준 등록·변경과 변경 시 재점검은 자동 점검의 전제라 함께 포함(backlog 공통 조건) |
| US-03 담당자가 분석 결과를 승인해 두 언어로 공개하기 | F-04, F-05 | 첫 데모 흐름 4단계. 모든 준비 건에 담당자 승인 필요(피드백 1), 두 언어 동시 표시(피드백 12) |
| US-04 담당자가 분석 결과를 반려하기 | F-04 | 반려 경로. LLM 결과가 틀렸을 때 이용자에게 공개되지 않게 막는 유일한 경로 |
| US-05 준비 상태를 체크하고 확인 요청하기 | F-06 | 첫 데모 흐름 5단계 |
| US-06 담당자가 보완 요청하고 이용자가 다시 준비하기 | F-07 | 되돌림 경로. 부족한 상태로 완료되는 것을 막음 |
| US-07 담당자가 준비 확인 완료하기 | F-07 | 첫 데모 흐름 6단계(끝 상태) |
| US-08 이용자가 진행 중인 준비 건 취소하기 | F-08 | 취소 경로. 모든 진행 상태에서 끝 상태로 가는 전이 |

다음은 MVP 범위 문서의 제외 항목과 이유다.

| 제외 항목 | 왜 뺐는가 | 나중에 넣으면 영향 범위 |
| --- | --- | --- |
| 회원가입·로그인·마이페이지 | 상태 전이·LLM과 관계없고, 권한 구분은 모의 계정 2개(이용자·담당자)로 테스트할 수 있음 | 인증 모듈 추가, 모든 API의 계정 확인 부분 교체 |

| 실제 서류·실명 정보 수집 | 동의·보관·삭제·마스킹 정책이 미확정(H4). 데모는 모의 서류만 사용 | 개인정보 처리 동의, 저장 암호화, 보관 기간·삭제 기능 |
| 실명·주소 자동 검출 | 패턴으로 검출할 수 없어 별도 모델이 필요함. 모의 서류만 쓰므로 MVP에서는 번호 패턴만 검사 | US-02 식별정보 검사 로직 교체, 오탐·미탐 테스트 추가 |
| F-6-1 외 체류 유형 | 유형마다 기준 목록과 검토자가 필요함. 한 유형으로 전체 흐름을 먼저 검증 | 기준 시드 데이터 추가, US-01 유형 선택지 확대 |
| 서류 진위 판정·개별 사건 법적 판단 | 서비스 범위 규칙 R1. 틀리면 이용자가 잘못 행동하고 책임을 질 수 없음 | 넣지 않음 (전문기관 안내로 대체) |

| 외부기관으로 정보 자동 전송 | 이용자 동의 범위와 수신 기관 협조가 확인되지 않음 | 동의 화면, 전송 이력, 외부 연동 |
| 대기·보완 알림(F-10) | 제안서에서 선택 기능. 화면 상태 표시만으로 첫 데모 흐름을 보여 줄 수 있음 | 알림 채널 동의, 발송 기능. 상태 전이에는 영향 없음 |

### 시연용 단순화와 제약

- 모의 이용자 1명과 지원 담당자 1명의 계정으로 역할을 구분한다. 회원가입·로그인·마이페이지 구현은 제외하지만 본인 건 접근, 담당자 승인 권한 검사는 유지한다.
- F-6-1 체류기간 연장 한 유형과 식별정보가 없는 가상 상황·모의 텍스트 PDF로 시연한다.
- 첫 데모는 미리 등록한 공통 기준 1개 버전을 사용한다. 관서별 기준의 실제 출처·갱신 책임은 미정이며, 확인되지 않은 요구를 만들어 내지 않는다.
- 한국어와 모국어 1개를 함께 표시한다. 첫 데모에 사용할 모국어는 미정이다.
- 첫 데모는 준비 건 생성부터 담당자 승인, 준비 확인 완료까지 보여 준다. 반려·보완·취소도 필수 인수 조건에 포함한다.
- 담당자 부재 중에는 자동 점검만 수행하고 승인 대기를 유지한다. 대체 승인 절차는 미정이다.
- 실제 서류의 동의·접근·마스킹·전송·보관·삭제 정책이 정해지기 전에는 실제 서류를 처리하지 않는다.

MVP 문서의 고객 요청 정리에서는 관서별 추가 기준을 공통 기준 시드로 대신한다고 적었지만, 같은 문서의 포함 표와 US-02 인수 조건에는 등록·변경 기능이 있다. 시연 데이터의 단순화와 기능 제외가 섞여 있으므로 팀이 범위를 맞춰야 한다. 준비 건 생성 시 템플릿 제공 요구도 포함·제외가 아직 정해지지 않았다.
