## 최종 선택

- 선택한 안: A안
- 프론트엔드: React·TypeScript
- 백엔드: Python·FastAPI
- DB: MySQL
- UI 도구: Figma
- 테스트 방식: pytest·FastAPI TestClient 기반 API 테스트. 입력 경계값·권한·상태 전이와 반려·보완·취소 경로를 확인하고, LLM 모의 응답으로 실패·지연·형식 오류를 재현한다.
- 시연·배포 환경: 첫 데모는 로컬에서 프론트엔드·FastAPI 서버·MySQL을 실행하는 웹 시연으로 준비한다(검토안). 외부 배포는 후속 운영 계획에서 정한다.

## 선택 이유 (팀 경험·기간·핵심 기능으로)
1. 팀에 FastAPI 사용 경험이 있어 개발하기 더 익숙하고 편하다. 이미 경험한 방식으로 API를 작성하고 오류를 해결할 수 있어, 처음부터 서버 구조를 익히는 부담을 줄일 수 있다. 이번 선택에서 가장 크게 본 기준이다.
2. 상황 설명·PDF 처리·LLM 연동을 Python 서버 안에서 이어 구현할 수 있다. 익숙한 환경에서 핵심 흐름을 먼저 연결해 3주차 첫 데모를 준비하고, 이후 승인·반려·보완·취소와 재점검 조건을 검증하는 데 시간을 쓴다.
3. React 화면 구현과 MySQL 사용 경험도 활용할 수 있다. 화면·서버·DB를 기존 경험에 맞춰 구성해 8주 안에 필수 기능을 완성하는 데 집중한다.

## 선택하지 않은 안과 이유
- B안은 Spring Boot·PostgreSQL을 사용하는 구성이다. 이번 프로젝트에서는 FastAPI가 팀에 더 익숙하고 개발하기 편하다는 판단을 우선해 A안을 선택했다. 서버 개발과 LLM 연동을 Python 중심으로 진행하는 편이 현재 팀 경험을 활용하기에 적합하다.

## LLM 연결

FastAPI 서버가 허용된 상황 설명·PDF 추출 텍스트와 등록된 기준을 LLM에 전달하고, 주의점·누락 가능성·추가 준비 서류 후보·근거를 분석 초안으로 저장한다. 식별정보·계정 정보·원본 PDF는 전송하지 않는다. 한국어·모국어 동시 표시는 구현하되 번역에 LLM을 쓸지는 번역 검증 방식과 함께 정한다.

입력 검사를 통과한 건은 서버 규칙에 따라 `준비중 → 자동 점검중 → 담당자 승인 대기`로 진행한다. 결과 공개를 위한 승인·반려·보완 판정·최종 완료는 담당자가 결정하고 서버가 권한·현재 상태·적용 버전을 검사한다. 취소나 입력·기준 변경 전의 분석 응답이 늦게 도착해도 현재 결과와 상태를 덮어쓰지 않도록 한다.

## 예상 어려움과 대응

| 어려움 | 대응 |
| --- | --- |
| React와 FastAPI 사이의 파일 업로드·입력·오류 응답 형식 불일치 | 요청·응답 형식과 거절 사유를 먼저 맞추고 모의 PDF로 정상·실패 응답을 함께 확인한다 |
| 분석 지연 중 중복 요청·취소·입력 변경으로 이전 결과가 반영되는 문제 | 준비 건의 현재 상태와 점검 당시 입력·기준 버전을 결과 저장 전에 검사하고, 취소되거나 버전이 다른 결과는 반영하지 않는다 |
| LLM 응답 형식 오류·근거 부족·분석 실패 | 서버에서 결과 형식과 근거 항목을 검사한다. 실패·확인 필요 사유를 담당자에게 표시하고, 해당 사유가 해소되기 전에는 승인으로 처리하지 않는다 |
| 승인되지 않은 분석이나 다른 이용자의 준비 건이 노출되는 문제 | 모의 계정으로 소유자·담당자 권한을 구분하고 화면과 API의 조회·변경 요청을 각각 검증한다 |
| 한국어와 모국어의 의미 차이 | 첫 데모 언어를 정하고 동일한 모의 사례의 두 언어 안내를 비교해 확인한다 |
| 팀원 컴퓨터마다 설치·실행 결과가 달라지는 문제 | 실제로 동작한 버전과 설치·실행 절차를 기록하고, 각자 같은 모의 자료로 실행해 본 결과를 scaffold-log.md에 남긴다 |
