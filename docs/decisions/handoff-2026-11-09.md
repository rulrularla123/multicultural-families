## 3. 남은 일

### 3-1. 입력 수정·재점검 (필수, 미착수)
근거: backlog US-04 (정상) 2, "정상 흐름과 공통 조건"의 상황·서류 변경 규칙, PRD 7절 "서류 변경과 동시 요청 처리"

- **서버**
  - 본인 이용자가 상황 설명·PDF를 고쳐 다시 제출하는 API (예: `POST /cases/{id}/inputs`, multipart, 경로는 API.md 합의 필요)
  - 입력 검사는 `case_detail.py`의 `check_situation`·`check_file_count`·`read_pdfs`·`check_display_language`(#82·#92)를 그대로 씀
  - 상황이 바뀌면 `situation_version`, PDF가 바뀌면 `document_version`을 올리고, 새 PDF는 새 `document_version`의 `Attachment`로 저장 (이전 첨부는 지우지 않음, 보관 정책 미정)
  - 이전 점검 결과·승인·확인 요청을 무효화하고 `current_check_task_id`를 비움. #98 `backend/app/common/criteria_changes.py`에 같은 무효화·재점검 처리가 있으니 재사용
  - 끝 상태(준비 확인 완료·취소 완료)는 409. 준비 여부 체크만 바꾼 것은 재점검하지 않음
  - 수정 전 점검의 늦은 응답이 저장되지 않는지 테스트 (#91 `test_workflow.py`의 늦은 응답 테스트 참고)
- **화면**: 반려된 건·준비중 건의 상세에서 상황 설명·PDF를 다시 내는 폼. 생성 화면(`CaseForm.tsx`)의 입력 부분 재사용
- **API.md**: 경로·입력·실패 응답 추가

### 3-3. 전체 흐름 검증 (MySQL)
- 내 Mac에는 MySQL이 없어서 #97·#100 화면은 **실제 백엔드 코드를 SQLite로 띄워** 브라우저로만 확인했다. MySQL에서 한 번 눌러 봐야 함
- 시나리오: 생성 → 점검 시작 → 담당자 검토·번역 확인 → 승인 → 이용자 결과(한·베) → 체크·확인 요청 → 완료(한·베 안내)
- 예외: 반려 → 수정 → 재점검 / 보완 → 수정 시작 → 재요청 / 각 상태에서 취소 / 기준 변경 뒤 재점검 / 끝 상태 이후 변경 거절
- 실행 전에 `python -m app.seed`로 모의 공통 기준을 넣어야 점검이 시작됨(#95). 기준이 없으면 점검이 409
- 각자 `docs/decisions/first-feature.md` 3절에 실행 결과 기록 (지금 1/5)

### 3-4. 알고 있는 빈 곳
- 실제 Gemini 연결 안 됨. 서버 기본은 외부 호출 없는 모의 응답(`MockTransport`). 모델 ID·키는 미정
- 생성할 때 자동 점검이 시작되지 않음. 이용자가 "자동 점검 시작"을 눌러야 함 (#91 설계)
- 취소 일시·취소 전 상태는 취소 직후 응답에만 있고 상세 API에는 없음
- 베트남어 번역은 담당자가 직접 입력·확인. LLM 번역·역번역 비교·고정 용어표는 제안만 하고 결정 안 됨 (PRD 미정 표)
- 재점검은 서버 프로세스 안 작업이라 서버를 다시 켜면 이어지지 않음 (#98 본문)
